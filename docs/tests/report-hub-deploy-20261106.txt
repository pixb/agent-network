换版前实测：`/health` 自报 **version=0.9.0-preview.144**，镜像 label =
`34cbb9a40b4bd…`，而这个提交**不在 pixb 的历史里**（`git merge-base --is-ancestor` 判否，
`git cat-file` 也取不到对象）。仓库里 `server/package.json` 是 `0.9.0-preview.265`。

⇒ 现网 hub 落后一截，其中直接可见的后果是 **#1298：hub 的 RUNTIMES 名单没跟着 pi-cli 改**，
`--runtime pi-cli` 在 hub 侧没有合法位置。这就是 AGENTS 里「部署身份 = pixb 源码提交」

## 顺带补上的缺口：进程自报构建标识（#3177 的 compose 版）

换版后第一件事就发现：label 正确，而

    /health  build_identified = false   commit = null

**label 是镜像元数据，进程读不到自己是谁**（#3177 在 npm 路径上已经处理过：prepack 写
`build-info.json`；compose 路径没做 ⇒ compose 构建的 hub 永远自报未识别）。

补齐：`Dockerfile.hub` 写 `/app/server/build-info.json`（`server/src/build-info.ts` 的读取点
是 moduleDir 与其父目录，两处都看）。

    {"schema":1,"commit":"93dfdeae7b4f24a18119868bb590df4890201041","dirty":false,
     "built_at":"2026-11-06T07:03:48Z","source":"compose_build_arg"}

⇒ `/health` 的 `build_identified = True`，鉴权视角可读到完整 sha。

### 第一版写坏了：手敲的 case 模式少一组括号

第一版判 sha 用 `case "$SOURCE_REV" in [0-9a-f][0-9a-f]…`（手写 40 组），
实测**只有 39 组** ⇒ 40 位 sha 永不匹配 ⇒ 静默走「不写文件」分支：
镜像 label 是对的，`/health` 仍自报未识别。是部署后 `docker exec cat` 核对才发现的。

改成 `grep -qE '^[0-9a-f]{40}$'` —— **数得出来的东西不要靠数**。
契约加门：判 sha 必须用 `{40}`；Dockerfile 里禁止出现 20 组以上手写重复括号
（`tests/compose-rebuild/compose-contract.sh`，48 条检查全部真正执行）。
drill 里新增两条判据就是这类缺陷的网：制品里必须有 40 位 sha 的 build-info.json、
进程必须自报 `build_identified=true`。
