3. 三条理由被测量改掉（不是改口味）
────────────────────────────────────────────────────────────────────────
  a) context「≤200 因为预览切 200」是错的：Dashboard 不渲染 task.context
     （TaskChatPanel.tsx / TaskDetail.tsx 从不读它），hub 接受 10000。
     context 的真实成本是 worker 的上下文 ⇒ 400，一行写完。
  b) 任务面板的 ≈12 行折叠（COLLAPSE_MAX_PX = 300，TaskChatPanel.tsx:601）是
     「展开全文 ⌄」按钮后面的折叠，不是永久遮蔽（:634-637）。
     ⇒ 交付正文的硬规矩是顺序：第 1 行结论、第 2–12 行证据、之后逐条验收、长报告落文件；
       不是「1200 以内才看得见」。
  c) 真正的悬崖是 hub 只存前 4000 字符（result/output 都是）。2400 是留余量，
     任何 >4000 的交付会被静默截断，所以 4000 写进 budgets.json 的 hard_constraints。

4. 被否掉的一条提案（写明理由，避免下次重提）
────────────────────────────────────────────────────────────────────────
  否：给 CJK 正文加 1.5–2× 字符系数（即中文正文按更宽的字符预算算）。
  理由：hub 的 zod 上限与存储截断都按 JS 字符数计；预览也是盲切字符数；
        CJK 约 1 token/字符，2× 字符数＝2× token 成本，且 Dashboard 拉丁宽度界面里中文是全宽。
  做法：预算继续按字符计；guard 输出 cjk 占比与 est_tokens 估算，让写正文的人自己看见代价。
  实测样例（本轮的演示正文）：575 字符，CJK 217（38%），est_tokens ≈ 306。

  - compose 机检 ttl ≥ 2× 节点 idle 预算（hub 不检查这条：默认 3600，上限 86400）。

  运营设计口径：派工时指针不要压得太短；它是**带 markdown 美化的摘要**（不是挤成一坨的纯文本），
  **不要行数限制**；详细任务写在任务文件里。

  改了什么（唯一来源 scripts/budgets.json，文档同口径）：
    task_lines_max 8 → **0（不限行数）**
    markdown 规则：全局禁 → **按行分级**
      line 1 必须纯文本（预览只显示它：sessions.task 盲切前 200 字符、节点卡 2 行、列表行 1 行）
