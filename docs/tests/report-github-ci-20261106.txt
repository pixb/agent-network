1. 这一周 CI 根本没跑：证据与判定
========================================================================
现象：parent 仓库所有 run（push + schedule）停在 2026-10-29（main b90e050f 三条 success），之后 0 条。
API 侧：
  GET /repos/pixb/agent-network/actions/permissions  ->  enabled=true  allowed=null
  GET /repos/pixb/agent-network/actions/workflows    ->  86 个全部 state=active
触发侧：
  gh workflow run <任意 workflow> -R pixb/agent-network -r pixb
    -> HTTP 422: Actions has been disabled for this repository.
判据：enabled=true 且 workflow 全 active，却在 dispatch 时被拒 => 压制不在仓库设置页里。
同期同一 token 对 pixb/agent-network-dashboard 的 dispatch 成功 => 不是组织层统一禁用，是单仓库。
组织层两个端点均 404（token 无 org 管理员权限）：orgs/pixb/actions/permissions、
orgs/pixb/settings/billing/actions => 组织层与账单只能由 owner 眼看。

2026-11-06 解除后实测：dispatch 成功进队列，run 42213359979 completed/success。

由此产生的长期手段：.github/workflows/ci-canary.yml（parent + dashboard 各一条）
  - 零 uses: 步骤（只有 echo）。dashboard 实测过这个区分：加 uses: 时被 allowlist 拒 ->
    startup_failure 且 jobs=[] 且无日志；零 uses 的 job 不受该原因影响。
  - 因此：canary 红 = 调度/runner/allowlist 问题；canary 绿而别的门红 = 代码问题。
  - 触发：gh workflow run ci-canary.yml -r <branch>；parent 版另挂 schedule（cron 23 * * * *）。

2.1 agent-node typecheck ratchet：新增 2 个身份 -> 新增 0
   - agent-node/src/runtime/pi-rpc/runtime.ts  TS2349 ×7（每个 removeListener?.()）
     根因：removeListener 只在 onRecord 闭包内被赋值/置空，TS 控制流分析看不到闭包内赋值，
     调用点类型收窄成 null；null?.() 的 callee 类型是 never => "This expression is not callable"。
     修法：读取放进 clearListener()（嵌套作用域内收窄重置回声明类型），顺带把「摘监听+置空」
     从 7 处展开收成 1 处。
   - agent-node/src/cli.ts  TS2345：goal routing 调用点传入的 union 含 "pi"，
     而 src/goals/routing.ts 的 GoalRoutingRuntime 只列 5 个 runtime。
     上游加 goal routing 时不知道有 pi。按 AGENTS 的「新增 runtime 是一张表」补齐 "pi"。
   验收（仓库自己的脚本，不是我重写判据）：

5. 残留红：Original frontdoor docs fixtures
========================================================================
失败点：step "Complete original render baseline and witnessed-red inputs" 内
  Error: Command failed: npm run build
  AssertionError [ERR_ASSERTION]: original frontdoor suite baseline failed
判据：该 workflow 要构建「原版」套件基线，依赖已发布的 npm 制品；pixb 不发 npm（AGENTS 规则），
所以这条在 pixb 上结构性地跑不通。它是既有设计，不是今天引入的（同一 head 上其它门全绿）。
处置建议：要么把该 workflow 限定成只在能取到发布制品的分支上跑，要么在 workflow 头部
写明「pixb 上预期不可运行」，避免将来把它当 required check 卡住合并。
